# Architecture and extension contract

Current priority: Apify and authorized direct-source APIs, with approved imports retained. Composio is optional. See `apify-collection.md` for the implemented Actor job/reservation/polling/import flow and its explicit live acceptance blockers.

`data/sources.json` is the versioned source catalog; `seed` inserts missing sources without overwriting operator permissions or schedules. Policy and schedule edits happen in PostgreSQL. Future catalog edits need an explicit reviewed migration to update existing rows.

The pipeline is: approved source export → validated connector → identity resolution → normalized private queue → due-source worker → PostgreSQL reviews + run log → authenticated dashboard. Each database transaction locks the relevant source; multiple workers use `FOR UPDATE SKIP LOCKED` to avoid processing a source simultaneously. Enqueue takes source/approval share locks and checks mapping; execution repeats the checks so revocation or expiry takes effect before ingestion.

`ConnectorRegistry` selects a collector by the source's method. The initial `ApprovedImportConnector` remains, tested using the explicitly named Capterra Reviews collection; Apify datasets now share its field validation and permission checks through a distinct `apify` method. The `apify` method now validates normalized provider datasets using the common review contract. Other method extension points are `authorized_api`, `permitted_crawl`, and `composio`. They raise `connector_unavailable` until an adapter is explicitly registered. A future polling adapter must also supply its source-specific job/input acquisition; the current worker consumes approved imports only. Do not claim that registering a class alone implements remote polling.

Before enabling another connector:

1. Discover official interfaces and connected account capabilities. Record the permission or license evidence, scopes, provider policy, permitted content, storage/retention rules, and approval expiry. For crawling, also review applicable terms, robots directives, allowed paths, fetch identity and provider rate limits. Do not treat robots permission as a license.
2. Add a connector with bounded inputs, request timeouts, pagination/checkpoint handling, data minimization and source-specific URL rules. Register only the reviewed method. Inject transport for tests; never log raw responses or credentials.
3. Resolve source product IDs through operator-approved mappings. Never merge on software names alone. Preserve provenance when content matches across sources. Existing fingerprint matching uses exact normalized text and date; it does not claim fuzzy or semantic deduplication. Cross-source duplicate groups need human review because boilerplate can match.
4. Raise `RateLimited(retry_after)` for 429 responses. Transient network adapters must implement bounded retry semantics, then let the scheduler defer. Permanent malformed imports are failed and cleared; resubmit corrected files. Database/process failures roll back transaction leases.
5. Add contract tests and a permission-approved live smoke test before declaring live support. Keep sources disabled until these pass.

Google Trends uses `trends_research`, never `reviews`. The SDK adapter, private integration bindings, normalized series projection, and status dashboard are implemented; real provider compatibility still requires credentialed discovery and review. The schema retains query, geography, time range, provider tool slug/version, original URL, response data, approval reference and timestamp. The implemented executor validates the discovered input schema, binds the connected account/user context and pinned toolkit version, and projects only allowed output fields. Additional output formats require their own reviewed normalizer. No session tool or catalog tool executes automatically during discovery. Other Composio integrations use the same explicit extension path.

Supabase is used as PostgreSQL via psycopg. This avoids exposing internal tables through REST. The schema owner applies migrations; a distinct server login inherits `veriflow_runtime` for the application. There are no public RLS policies or auth-user metadata decisions. The private admin UI uses a separate HTTP credential at the perimeter, with all database operations server-side. Future public APIs and WordPress/custom frontends can consume a separate curated export/API without changing the internal collection model. They must never receive the runtime database credentials.
